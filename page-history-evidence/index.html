Page history and audit log for Confluence

What happened to this document — including the moves, the deletions and the attachments that Confluence's own history leaves out.

Confluence's built-in audit log covers spaces, permissions, users and settings. Atlassian's own documentation says it “doesn't record information related to content edits or changes to a content's location”. So when an auditor asks what happened to a particular document, the answer is not in it.

Page History & Audit Log is being published to the Atlassian Marketplace. The install link will appear here as soon as the listing is approved.

What it records

From the moment it is installed, it keeps its own content-level history from the events Confluence emits:

  • Page history — created, updated, moved between spaces, copied, archived, restored, and permission changes, each with the version number, the person and the time
  • Deleted pages and trash details — trashed, restored and deleted, so a page that is gone still has a record
  • Attachment history — on the same timeline as the page it belongs to, with file size and type
  • State on a date — what a page's version and status were on a given day, replayed from the events
  • An evidence pack — exported as CSV, with its own caveats written inside the file rather than left behind

It tells you when it is incomplete

An audit log is a commodity. The admission that a log has a hole in it is not.

When this app cannot record something — a failed write, an event it cannot read, an event with no page attached — it stores a gap marker, and the report shows it at the top of every screen. A trail that is used as evidence should state its own completeness, rather than look clean because something went missing quietly.

What it does not do, stated plainly

  • It records from installation onward. History from before that was never sent to it and cannot be recovered.
  • Confluence does not emit cascading deletion events, so a page removed together with its space is reported from the space record and labelled as an inference, not as a recorded page event.
  • It does not record page views or likes. Enormous volume, no evidentiary value.
  • It cannot tell you why something was deleted. Confluence does not collect a reason, so nobody can report one.

Permissions, including the awkward one

This app does not write to Confluence. It requests one write scope, write:confluence-content, for a single reason: Atlassian requires that scope in order to deliver page “trashed” and “deleted” events to a Forge app. It is a requirement for receiving the notification, not for performing an action, and Atlassian's own events reference notes the requirement “may be removed in the future”.

Without it the app would stop recording the moment a page is deleted, which is precisely the failure an evidence trail exists to prevent. We would rather ask for the scope and explain it here than quietly ship a log with a hole where the deletions should be.

The only outbound request this app makes, other than reading events, is asking Confluence whether the person viewing a report is allowed to see a given page — before any of that page's history is shown. It never creates, edits, moves, restricts or deletes anything.

Where your data sits

  • Runs on Atlassian Forge, inside Atlassian — eligible for Runs on Atlassian
  • No application server of ours, and no external storage of your content
  • No egress to any host outside the Atlassian product APIs
  • Page content itself is never stored — only the fact that an event happened, its version number, its timestamp and who caused it
